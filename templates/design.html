Design principles, priorities & tools

The constraints Bench is built to, the order they win in when they pull against each other, and the full catalog of tools the agent can call.

How data flows

Principle 2 as a picture: almost everything lives inside the browser. The only thing that ever crosses the network is masked chat text and a tool schema — never a file, a dataframe, or a raw cell value.

Design principles

Seven constraints the architecture is built around — not aspirations, things the code has to satisfy for the product to be what it claims to be.

1

Real execution, not talk

The agent has tools and a live Python/R environment to actually do data analysis, not just describe what it would do.

2

Data never leaves the client

Uploaded files, parsed dataframes, and all intermediate analysis state live only in the browser (OPFS/IndexedDB). The server never receives, stores, or processes the user's data.

3

Tool calls & execution run client-side

Every tool dispatch and every line of code runs in the browser — Pyodide/webR workers — never on the server, regardless of which model provider is configured.

4

Client-side redaction

Rows, columns, or individual cells can be marked hidden. Whatever the model ends up seeing — tool results, code output, previews, charts — has those values stripped first, at a single sanitize() choke point.

5

One Dockerfile, one container

No docker-compose, no side services. The frontend build, the relay backend, and every execution engine ship inside one Dockerfile as static assets plus a single Python process.

6

Provider choice, including full bypass

Route through the hosted proxy, or point the agent at your own API-compatible endpoint — including a local model on your own machine. In that mode, the backend is never contacted at all.

7

Minimal, non-content metadata when hosted

Routing through the hosted proxy may log basic operational metadata — dataset shape, tool names, model/timing stats — but never the data itself, or anything derived from cell contents.

Priorities

The principles above don't always pull the same direction. This is the order they're resolved in — read top to bottom as "wins over everything below it."

  1. 1

    Privacy is non-negotiable

    No feature ships if it requires sending user data off-device, even for convenience. It's why charts are structured Vega-Lite specs instead of raster pixels — a spec can still be masked before render; a PNG can't.

  2. 2

    Correctness over convenience

    The agent states its assumptions and proceeds by default. It only stops to ask when a point is genuinely ambiguous, the data can't resolve it, and the choice materially changes the result. A question on every turn is a failure mode — a question that prevents a wrong primary result is the win.

  3. 3

    Structured data over freeform text

    Tool results come back as {columns, rows}-shaped payloads and inspectable specs wherever possible, not prose — a value can be masked or lint-rejected before it's serialized, but not after it's already flattened into a string.

  4. 4

    Evidence before trusting a prompt or tool change

    Changes to the system prompt or tool catalog run through the eval harness (standalone smoke test, then the full browser harness) before being treated as settled — a hand-edit is a proposal until the eval tiers confirm it didn't regress analytical rigor.

  5. 5

    Small, auditable backend surface

    The server is a stateless LLM proxy plus a few static pages — no session state, no body logging. Small enough to read in one sitting and reason about exactly what it could leak.

Tool catalog

Everything the agent can call, grouped by purpose. All of it runs client-side (principle 3) and is masking-aware (principle 4) — the tables below note what still gets filtered before the model sees it.

Execution

Tool Args Returns Notes
run_python { code } stdout, dataframe previews, plot images Pyodide/WASM worker; persistent namespace across calls in a session
run_r { code } stdout, dataframe previews, plot images webR/WASM worker; same execution model as run_python

Navigation & introspection

Read-only, side-effect-free — cut down on the model burning turns re-orienting itself (e.g. re-listing files, reloading a dataset it already has).

Tool Args Returns Masking
get_file_tree {} Datasets in OPFS + virtual FS: name, size, ext, row/col counts No cell content; filenames not sent as metadata
describe_dataset { filename } Column names, dtypes, row/col counts, null counts Value samples through sanitize()
preview_file { filename, n=10 } First n rows as { columns, rows } Forbidden literals scrubbed before return
read_text_file { filename, max_bytes } UTF-8 text of a small non-tabular file Through sanitize(); size-capped
list_variables { engine } Names/types/shapes of live dataframes & vars Names & shapes only, never values
column_stats { filename, column } count/mean/std/quantiles/top categories Through sanitize(); steered away from masked columns

Visualization

Interactive, theme-aware, and — unlike a static plot image — structured enough to mask and lint before it ever renders.

Tool Args Renders Guardrail
render_chart { spec, description } Interactive Vega-Lite SVG chart inline in chat 500-point cap; rejects specs referencing a masked column, with an error the model can recover from
render_table { columns, rows, description } Sortable, scrollable, theme-aware table Rows routed through sanitize()

Human-in-the-loop

A tool call that pauses and asks, rather than guesses. Governed by priority 2 above — this is a last resort for genuine unknowns, not a substitute for the agent's own judgment.

Tool Args Returns Use for
ask_user { question, why? } { answered, answer } Free-text clarification (e.g. what a domain term means)
ask_choice { question, options[], allow_multiple? } { answered, selected[] } Disambiguation (e.g. which column is the treatment arm)
confirm { question, detail? } { answered, confirmed } Yes/no before a consequential, hard-to-undo step
clarify_term choose_column confirm_exclusion — thin, better-labeled presets over the three primitives above, same mechanism

Every card carries a "Let you decide" control the user can always hit instead of answering, and every request auto-resolves as answered: false after 10 minutes or on Stop — a HITL tool call never actually blocks the agent, it only offers it better information when a human is there to give it.
